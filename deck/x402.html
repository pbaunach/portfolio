02Architecture

Four parties, and only one of them holds a key

1 · The calling agent

Never sees a 402

Claude Code, Cursor, anything speaking MCP. It never signs anything and never holds a wallet.

2 · The MCP server

Plays the client half

Holds the agent keypair. @x402/fetch catches the challenge, signs and retries, then stamps the license onto its own copy.

3 · The resource server

Quotes and withholds

Prices the route and releases the asset on settlement. Holds no secret key, only the vault's public address.

4 · Facilitator and ledger

Verifies and submits

An OpenZeppelin-hosted testnet facilitator checks the envelope, submits it, and pays the network fee, so the agent needs USDC but not XLM.

Why it splits this wayThe server cannot spend and the agent cannot self-certify. The only party holding a key is the one whose money moves.

03Protocol

The round trip, header by header

MCP SERVER                                        RESOURCE SERVER
    |                                                           |
    |--- 1  GET /icons/vector-db ------------------------------>|   no payment yet
    |                                                           |
    |<--- 2  402  PAYMENT-REQUIRED -----------------------------|   scheme, payTo, amount
    |           body: tier, price, tags, preview_url            |   free to read
    |                                                           |
    |--- 3  GET  X-PAYMENT: signed envelope ------------------->|   agent wallet signs
    |        [ facilitator:  verify -> submit -> close ]        |   ~5s, the floor
    |                                                           |
    |<--- 4  200  PAYMENT-RESPONSE: tx hash --------------------|   asset released
    |                                                           |

Two headers carry the protocol

PAYMENT-REQUIRED going out, PAYMENT-RESPONSE coming back. Both are base64 JSON, and the second one is where the transaction hash arrives.

The retry is the payment

There is no second endpoint and no checkout. The same GET is repeated with a signed envelope attached.

Settlement gates the body

The route handler runs, but nothing reaches the caller until the facilitator confirms the transfer cleared.

05Protocol

One endpoint, three prices

"GET /icons/:iconId": {  accepts: {    scheme: "exact",    payTo: config.vaultPublicKey,    price: (ctx) => getIcon(idFrom(ctx.path))             ?.price ?? TIERS.standard.price,    network: "stellar:testnet",  },  // the free assessment payload  unpaidResponseBody: (ctx) => ({ … }),}

Price is a function, not a constant

The x402 route config takes a callback, so one route quotes three tiers: $0.000, $0.002 and $0.010.

The tier belongs to the asset

Not to the endpoint. Adding a tier is catalogue data, not a new route and not a new contract.

The quote is what settles

test:pricing asserts both halves: that standard and premium are quoted and settled at their tier price, checked on Horizon rather than in our own logs.

06Soroban

USDC on Stellar is a contract, not a balance

The token is a contract

Paying means invoking

USDC is reached through a Stellar Asset Contract, the stock token contract every asset gets. Settling is a transfer invocation, not a classic payment operation.

The agent authorizes it

Signed, then submitted

The Stellar scheme builds the invocation and an Ed25519 signer authorizes it. The facilitator submits it and pays the fee, so the agent needs USDC but not XLM.

The ledger reads oddly

Where it actually shows up

It lands as invoke_host_function, with the real from, to and amount inside asset_balance_changes. Anything reading Horizon must handle both shapes.

Worth knowingUSDC carries 7 decimals on Stellar, so prices are integers underneath: $0.002 is 20,000 atomic units. Basket totals are summed in those units and only then formatted, which is why a 25-icon total is exact rather than a float that drifts.

08Latency

One settlement, twenty-five assets

 20 icons as one basket   8.06s   versus roughly 180s one at a time

Latency is per settlement

Not per icon. A twenty-icon basket costs about the same wall time as buying one, because it waits for one ledger close instead of twenty.

The basket keeps the ordering

An unknown id rejects the whole basket before the middleware, so nothing is charged. Free icons ride along at no cost.

The tool says so itself

fetch_vector_icons explains the tradeoff in its own description, so a calling agent has a reason to prefer the basket.

09Provenance

The payer writes the receipt

<svg  data-va-asset="vector-db"  data-va-license="standard"  data-va-tx="0a0155746e73…ccfb"  data-va-network="stellar:testnet">  <!-- paths --></svg>

The MCP server stamps it, not the server

The Stellar scheme settles after the route handler has built its body, so the resource server cannot know the hash yet. The payer can.

The network attribute is load-bearing

A bare hash is meaningless without knowing which ledger to resolve it against, and resolving it is the entire point.

Free assets are stamped too

With a tier and no citation. The claim is that an audit finds zero unattributed assets, and "free" answers the question while a missing attribute does not.

10Provenance

Resolved against the ledger, never against us

What resolving proves

Facts read off Horizon

A settled transfer, of this amount, to this account, at this time. The verifier additionally checks the amount matches the asset's tier price. None of it asks VectorAgent anything, so the audit still works if the company is gone.

> npx tsx scripts/audit-licenses.ts ./src

What it does not prove

The gap that is still open

That the transfer bought this icon. The asset id is not carried inside the transaction, so that link still comes from our records. A basket is looser again: one settlement covers the total, so a verifier can only check this asset's price fits inside it.

Closing itThe asset id has to travel with the money, either in a Stellar memo or inside a contract call. That is the next slide, and it is the real argument for writing a contract rather than using the stock one.

11Soroban · Design

What a contract of our own would close

Gap 1 · Binding

Put the asset id in the ledger

A purchase(asset_id, amount) entry point writes the id into the entry itself. The citation stops being "a payment of the right size" and becomes proof this payment bought this asset.

Gap 2 · The split

Pay the creator in the same call

The 90/10 split lives in our accounting today, which means trusting us. One invocation paying both parties makes the royalty as checkable as the purchase.

Gap 3 · Baskets

Receipt the whole basket

A manifest hash in the call lets a verifier confirm an asset was in the basket that settled, instead of checking only that the total was large enough to cover it.

Not builtThere is no contract source in the PoC. Settlement today uses the stock Stellar Asset Contract, which is why the binding gap exists at all. A contract of our own adds a deployment, an upgrade story and an audit surface, and none of those are free: it buys verifiability, and it costs trust that has to be re-earned in code.

12Open

Three things the rail does not solve

01 · Overhead

The facilitator half

Up to 4.8 seconds after the money has already moved. It is the removable half of the wait, and PayAI took x402 on Base from 1.7s to 750ms by chasing exactly this.

02 · First contact

The genuine one-off

An agent that has never paid us before, with no funded wallet, wanting one asset once. No deployed x402 pattern solves this without pre-funding.

03 · The tempting shortcut

Release on verification

Handing the asset over once the envelope verifies, before it settles, is what we reached for first. A production deployment measured 86.95% leakage under burst. It is a vulnerability class, not a pattern.

The loop works and the money is real.

What is unfinished is speed, onboarding and binding.
